# GDScript 注解规范：`@tool` 与 `class_name`

> **用途**：为 Godot 4 插件 / 编辑器工具中的两个「全局契约类注解」给出统一准入标准，避免把注解当成"保险"随手添加，也避免在大规模脚本里失去尺度。
> **适用**：项目内全部 GDScript，跨插件通用。
> **核心结论**：两者互不替代，**默认都不加**，只在「跨边界」时加 —— 不跨"编辑器 / 运行时"边界就不加 `@tool`，不需要跨文件按名字引用就不用 `class_name`。

---

## 一、各自解决什么问题

| 注解 | 回答的问题 | 生效范围 | 加错的后果 |
|------|-----------|---------|------------|
| `@tool` | 这段代码能不能在**编辑器进程**里执行 | 由引擎替脚本创建实例的路径（场景节点、资源文件、`EditorPlugin` / `EditorScript` 加载） | 编辑器被当作运行时：真实执行、真实写盘、可能崩溃 |
| `class_name` | 这个名字能不能被**全项目按名字**找到 | ScriptServer 全局类表（与用户项目、其它插件**共享**同一名字池） | 命名撞车导致加载报错；全局表被内部实现占满 |

三条容易忽略的性质：

1. **互不替代** —— `class_name` 不会让脚本在编辑器里跑，`@tool` 也不会让名字全局可见。
2. **不传染** —— 继承一个 `@tool` 父类**不会**让子类进入 tool 模式，每个文件都要自己写；反过来，父类不是 `@tool` 也不妨碍子类声明 `@tool`。
3. **都是"提升"** —— 两者都把局部的东西提升为全局契约，因此默认应当**不提升**。

## 二、`@tool` 准入

### 2.1 先理解机制：只有两条创建实例的路径

| 路径 | 谁创建实例 | 非 `@tool` 脚本的表现 |
|------|-----------|----------------------|
| **引擎代创建**：加载场景 / `PackedScene.instantiate()` / 加载资源文件 / 编辑器加载插件脚本 | `Object::set_script()`，并检查 `Script::can_instantiate()` | 退化为**占位实例**：属性可见、方法不可调、`_ready` / `_process` / `setter` 不执行；`EditorPlugin` 则直接加载失败 |
| **代码自创建**：`Xxx.new()` | `GDScript::_new()`，**不查** `can_instantiate()` | 正常工作 |

由此可得：`@tool` 只在「引擎替脚本创建实例」这条路径上才有意义。**被编辑器加载的脚本**需要它，**只被 `new()` 出来的脚本**不需要它。

### 2.2 必须加（4 种情形）

| # | 情形 | 说明 |
|---|------|------|
| 1 | 脚本挂在 `.tscn` 的节点上 | 编辑器打开场景 / 代码 `instantiate()` 时都会走 `set_script()` |
| 2 | 脚本是 `.tres` / `.res` 的资源脚本 | 同上；不加则"资源字段在、行为不在"（`setter`、方法全失效） |
| 3 | `EditorPlugin` / `EditorScript` | 编辑器加载插件脚本前会显式检查可实例化性，`plugin.gd` 不加则插件无法启用 |
| 4 | 编辑器中的其它代码会调用它的方法 / 读它的字段 / 依赖它的 `setter` | 占位实例没有脚本方法，调用只会**静默失效** |

### 2.3 不需要加

| 情形 | 说明 |
|------|------|
| 只由代码 `Xxx.new()` 创建（服务类、命令/工具类、纯数据类） | 走 `_new()` 路径，不受工具模式限制 |
| 纯静态类（全部成员为 `const` / `static var` / `static func`） | 静态方法、常量在非 `@tool` 脚本中均可调用 |
| 仅被其它脚本静态调用的工具集 | 同上 |

> 边界例外：官方文档提示"非 tool 脚本读取静态变量可能得到 `null`"。该行为随引擎版本而异，**若某类依赖静态状态且被编辑器代码访问，保守加上 `@tool`**。

### 2.4 为什么默认不加

`@tool` 不是"标注"，而是**风险声明**：被标注脚本的代码会在编辑器进程里真实执行。

- 编辑器没有为 `@tool` 提供保护，误用 `queue_free`、改写场景、调用编辑器接口都可能导致崩溃或不可撤销的修改；
- 加得越多，编辑器里"本该只属于运行时"的代码越多，调试面越大；
- 判断标准是**"是否被引擎装载"**，不是"这段代码是不是我写的"。

## 三、`class_name` 准入

### 3.1 门槛：确实需要「跨文件按名字引用」

| 需求 | 说明 |
|------|------|
| 类型标注 | `var a: Foo`、`Array[Foo]`、`x is Foo` |
| 全项目调用入口 | 静态工具类、全局服务的外观方法 |
| 编辑器 UI 可见 | 继承 `Node` → 出现在"新建节点"；继承 `Resource` → 出现在"新建资源" |
| 场景 / 资源按类型识别 | 自定义 `Resource` 被 `.tres` 引用 |

不满足以上任一项时，用文件内常量即可，不必上升到全局。

### 3.2 替代方案：`preload` 常量

```gdscript
# --- Constants ---
const SomeHelper := preload("res://path/to/some_helper.gd")

var helper: SomeHelper = SomeHelper.new()
```

优点：同样支持类型标注、不占全局名字、改名不会影响其它文件的外部引用。
**只在少数文件使用的工具类，优先用它。**

#### 3.2.1 三条硬约束（此时 `class_name` 无法被替代）

| # | 约束 | 说明 |
|---|------|------|
| 1 | `Array[X]` / `Dictionary[.., X]` | 元素类型必须在编译期从**全局作用域**解析，`const` 别名不参与该解析，会报类型找不到 |
| 2 | `X.InnerClass` / `X.InnerEnum` 作为类型位置 | 命名空间式访问依赖全局类名（内嵌类型无法通过别名解析） |
| 3 | 声明文件内部的代码级自引用 | 典型是 `static func create(...) -> 自身类名`；去掉 `class_name` 后返回类型无法解析 |

> 判定提示：脚本内**字符串**中的类名（日志 tag、节点名字符串）不构成自引用，判断前应先剔除字符串字面量。

### 3.3 命名：插件必须自带前缀

`class_name` 进入的是**与用户项目、其它插件共享**的全局类表：

- 插件内新增的全局类一律加项目前缀（如 `MyPluginXxx`），避免与用户代码或其它 addon 撞名；
- 泛用词（`Manager`、`Controller`、`Config`、`Utils`、`Helper`）尤其危险；
- 频率极高、改名成本大于收益的核心类可以保留原状，但**新代码不要模仿**这些命名。

### 3.4 改名注意

- **`class_name` 与文件名解耦**：场景 / 资源文件里记录的是**脚本路径**而不是类名，因此改类名通常不需要改文件名；
- 但脚本内所有类型标注、`is` 判断、`Array[T]`、枚举/内嵌类型访问都要同步；
- **节点名（`$Node` / `%Node` / `get_node("Node")`）与类名解耦**，批量改名时务必排除节点名与字符串字面量，否则会在运行时报"节点未找到"。

## 四、按层决策（通用台账）

不逐个文件纠结，只按"这个脚本在架构里的角色"决定：

| 层 | 典型角色 | `@tool` | `class_name` |
|----|---------|---------|--------------|
| 插件入口 | `EditorPlugin` 主脚本 | ✅ 必须 | ❌（配置文件按路径加载它） |
| 编辑器扩展 | 导出插件、调试器插件、`EditorScript` | ✅（同族一致 + 静态状态风险） | ❌ |
| 场景 / UI 节点 | 面板、窗口、消息块等挂在 `.tscn` 上的脚本 | ✅ 必须 | 仅当被其它脚本按类型引用 |
| 数据资源 | 继承 `Resource`、被 `.tres` 保存与加载 | ✅ 必须 | ✅ 必须（类型标注 + 资源对话框） |
| 命令 / 工具集 | 由注册表按路径加载并 `new()` 的执行单元 | ❌ | ❌（"路径即 ID"，无需全局名） |
| 纯静态工具 | 日志、路径、文件读写、解析器等 | ❌ | 按引用广度决定 |

> 工具层的标准形态：**一个有 `class_name` 的基类 + 一堆无名子类**。既保留 `x is Base` / `Array[Base]` 的能力，又让几十个具体实现不占用全局名字。

## 五、5 问准入清单

**`@tool`**

1. 会被 `.tscn` 挂到节点上吗？
2. 会被 `.tres` / `.res` 当资源脚本加载吗？
3. 会被编辑器加载（EditorPlugin / EditorScript）吗？
4. 编辑器中的其它代码会调用它的方法 / 读字段 / 依赖 `setter` 吗？

→ **任一 yes 才加**，全 no 不加。

**`class_name`**

1. 需要被多个文件、或跨目录按类型引用吗？
2. 需要出现在"新建节点 / 新建资源"对话框里，或被 `.tres` 按类型识别吗？
3. 名字带了插件前缀、确认不会撞车吗？

→ **全 yes 才加**，否则用 `preload` 常量（注意 §3.2.1 三条硬约束）。

## 六、自查方法

| 检查项 | 做法 |
|--------|------|
| `@tool` 是否齐备 | 列出所有 `.tscn` / `.tres` 引用的脚本，逐个确认有 `@tool`；插件主脚本必须有 |
| `@tool` 是否多余 | 逐个对照 §2.2，未命中且从不被引擎装载的，可去掉 |
| 找出纯静态类 | 对比 `static func` 与 `func` 的行号集合：两者一致且无 `_init` ⇒ 全部函数为静态 |
| `class_name` 是否过多 | 统计"声明了 `class_name` 但只被 1~2 个文件引用"的类，改为 `preload` 常量 |
| 改名安全性 | 替换前排除 `$Node` / `%Node` / 字符串字面量 / 节点名 |

## 七、常见误区

| 误区 | 实际情况 |
|------|---------|
| "统一全加 `@tool` 更保险" | 它是风险声明；只在被引擎装载时才值这个风险 |
| "`@tool` 会传染，父类加了子类就不用加" | 不会传染，子类必须自己声明 |
| "`class_name` 能提升性能" | 不能；它只是全局名字注册，`preload` 常量同样可做类型标注 |
| "删掉 `class_name` 一定安全" | `Array[X]`、`X.InnerClass`、自身返回类型三处会直接编译失败（§3.2.1） |
| "未被引擎装载的脚本不加 `@tool` 一定安全" | 只要将来它被挂到场景 / 资源上，就会退化成占位实例，且**不报错**（表现为方法静默失效） |
| "去掉 `@tool` 后当前会话就跑不起来" | 实例可能仍是旧脚本版本，**必须停用插件或重启编辑器**后再验证 |

---

## 八、如何验证（最小实验）

1. 选一个**只经 `new()` 创建**的脚本，临时去掉 `@tool`；
2. **停用插件 / 重启编辑器**（关键：避免旧实例掩盖问题）；
3. 触发该脚本对应功能，同时观察输出面板是否有"无法实例化"类报错；
4. 若正常 → 该类确实不需要 `@tool`；若异常 → 说明它实际走了引擎装载路径。

反向验证场景 / 资源脚本：去掉 `@tool` 后重新打开场景，观察节点是否正确初始化、方法是否还能被编辑器代码调用。
