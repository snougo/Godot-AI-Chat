# 工具调用反馈：用返回值校准模型行为

## 何时读这份文档

设计或修改 AI 工具的返回结果、工具描述时；或遇到「工具返回值正确，但模型据此得出的结论是错的」这类问题时。

---

## 核心思路

工具描述与参数描述保持简洁，复杂的校准信息交给**调用返回的结果**。

一句话分工：

> **描述负责「该不该用我」，返回值负责「这个结果该怎么读」。**

---

## 为什么用返回值

| 优势 | 说明 |
|---|---|
| 时机 | 出现在模型做判断的那一刻，不需要它主动想起去查文档 |
| 时效 | 与实现同源，实现改了返回值里的描述自动跟着改，不会过时 |
| 条件触发 | 只在异常时出现，日常调用完全不受干扰 |

---

## 边界：返回值校准不了「路由」

返回值能说「这个结果不完整」，但无法说「你可能用错了工具」。

最危险的形态是**沉默**：工具返回一份干净、完整、格式正常的结果，只是少了一整类内容。缺失不可见，因此没有任何信号可以触发校准。

实例：`push_error()` / `push_warning()` **从不写入**编辑器 Output 面板。调用 `read_output` 得到一份零错误的日志时，不会出现任何提示——「以为没报错」就这样发生了。

> 结论：**缺少信号的知识必须前置**，放进工具描述，一个从句即可，不需要长篇。

---

## 分派规则

| 知识类型 | 返回结果里的信号 | 落点 |
|---|---|---|
| 有信号且清晰 | 能被读出来 | 返回结果（条件触发） |
| 有信号且自解释 | 读者一看就懂（如 `… (+20 more chars)`） | 返回结果，不必额外处理 |
| 有信号但答案是错的 | 输出形式正常、内容判错 | **改行为**：在结果里标注判定依据 |
| 无信号 | 缺失不可见 | 工具描述（前置路由） |
| 低频、无信号、跨工具 | —— | 文档 |

---

## 返回结果的措辞要求

1. **条件触发**：与异常同生共死。每次调用都固定出现的免责声明会退化成噪音，被习惯性忽略。
2. **正面否定错误结论**，而不是给免责声明：
   - 好：「显示为空，但视图控件把所有内容过滤掉了——这不能说明实际打印了什么」
   - 差：「结果可能不完整，请注意」
3. **不确定性前置**：把「这份结果不是全量」放在**第一行**，而不是文末。模型常常读完主句就开始下结论，末尾的 Note 拦不住它。
4. **为空时解释原因**：说清是「真的没有」还是「看不见」。这两件事绝不能用同一句话表达。

---

## 哪些工具需要这套处理

判断标准：**返回值是否为代理指标（proxy）**——它返回的不是事实本身，而是事实的一个视图或子集。

需要：

- 读取界面上「用户此刻看到的东西」（如 Output 面板）
- 只返回子集的查询（行数上限、深度上限、搜索结果）
- 多数据源并列、可能存在「该改用另一个」的工具族
- 容易静默失败的操作

不需要：返回值即事实的直接动作型工具（写文件、创建节点、启动游戏）。

## 案例：read_output

`read_output` 的返回值来自 Output 面板的 `get_parsed_text()`——用户眼前那份文本，典型的代理指标。它继承了两类偏差：

1. 面板视图控件（消息类型过滤按钮、搜索框）会让行**彻底消失**，且不进入统计
2. 单行超过 400 字符会被折叠

原实现只把限制挂在文末 `Note:` 里，主句照样输出 `20 lines (20 prints, 0 errors, 0 warnings)`——一份看起来完整干净的日志，实际有 65 行、4 个错误。

修复后：

- 视图受限时，**第一行**输出 `[PARTIAL] The panel is filtered: the counts and lines below describe only what it currently shows, never the whole log.`
- 面板为空且被过滤时，改为「显示为空，但视图控件把内容全过滤了——这不能说明实际打印了什么」，不再断言「从没打印过」
- 未受限时输出完全不变（零噪音）

而「`push_*` 只能从 `read_errors` 获取」这条无法靠返回值传达，留在 `tool_description` 里作为一个从句。

## 案例：read_errors（同一事实分散在多个面板）

Debugger 面板把「错误」拆成两个互不相通的通道：

| 通道 | 内容 | 可见时机 |
|---|---|---|
| Errors 标签页的 Tree | 错误/警告条目 + 源码行 + 栈帧 | 错误落地后 |
| Stack Trace 标签页的 reason 横幅 | 当前暂停原因 / 会话状态串 | 引擎写入即覆盖，会话开始时是样板文本 |

同一个解析错误在这两个通道里是**互斥出现**的：断点暂停中只在横幅里，继续执行后才进 Errors 树。由此得到三条：

- 工具必须读全通道再拼接结果。任何「只读一个面板」的实现，都会在某些运行状态下给出干净的「一切正常」——最危险的那种沉默。
- 描述里不能写死「只在哪里」，要写成带条件的句子（「暂停中只有横幅有它，继续执行后进 Errors 列表」）。
- 落点取决于**运行状态**（Ignore Error Breaks 开/关、是否已继续），不取决于代码路径，读代码推不出来。这类工具必须实际跑起来、切开关、逐状态复现才能定稿。

### 噪音过滤的方向

reason 横幅混着会话状态串（`Debug session started.`），必须过滤，否则每次调用都带一行噪音。两个方向的风险不对称：

| 做法 | 例 | 结果 |
|---|---|---|
| 白名单：只中继「看起来是错误」的文本 | `text.contains("error")` | **静默丢掉真信号** —— `Cannot call method 'get_name' on a null value.` 不含 "error"，直接消失 |
| 黑名单：只排除已知样板值 | `REASON_NOISE.has(text)` | 未知变体最多多一行，不丢信息 |

选黑名单。判据是「丢一个真信号」远比「多一行噪音」严重：前者让模型得出「没有错误」的错误结论，后者只是冗余。

---

## 反面清单

- 在 `tool_description` 里复述参数 schema 已有的信息（纯冗余，白占位置）
- 用一句「注意」代替改变行为（返回错的答案 + 提示「可能不准」＝ 模型两头都看见了，仍可能选错）
- 把校准信息写成每次必带的免责声明
- 把「结果不完整」埋在文末
- 用「看起来像错误」的启发式筛选信号（白名单过滤）——漏掉的恰好是措辞不典型的真错误
